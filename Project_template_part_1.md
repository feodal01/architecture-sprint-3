# Задание 1. Анализ и планирование

Чтобы составить документ с описанием текущей архитектуры приложения, можно часть информации взять из описания компании условия задания. Это нормально.

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут включить и отключить отопление, установить целевую температуру - HeatingSystemController
- Система поддерживает логирование операций с системой отопления, сохранение состояния отопительной системы (ид, вкл/выкл, целевая температура, текущая температура)

**Мониторинг температуры:**

- Пользователи могут просматривать текущие показания температурных датчиков через HeatingSystemService
- Система поддерживает сохранение показаний датчиков в таблице temperature_sensors с данными ид, температура, дата-время последнего обновление
- обновление показаний датчиков происходит через запрос сервера к датчику

### 2. Анализ архитектуры монолитного приложения

Перечислите здесь основные особенности текущего приложения: какой язык программирования используется, какая база данных, как организовано взаимодействие между компонентами и так далее.

- Монолит на Java 17 с Spring Boot
- используется Maven 
- БД - PostgreSQL с таблицами heating_systems и temperature_sensors
- используется DTO для передачи данных - HeatingSystemDto
- Деплой производится с использованем docker
- Ci/CD настроен через Guthub Actions
- REST API как основной метод работы, нет асихнонных вызовов
- Все данные получаются через запрос сервера к датчику
- самостоятельно подключить датчик пользователь не может

### 3. Определение доменов и границы контекстов

Опишите здесь домены, которые вы выделили.

1) Подключение/отключение устройств умного дома (температурные датчики и не только в последующем) (CREATE / DELETE) - невозможно самим пользователем
2) Управление подключенными устройствами - включить/выключить или изменить какие-то параметры устройства если они есть (UPDATE) - есть в системе только для отопления
3) Сбор показаний датчиков - с подключенных датчиков сохраняется информация для последующего использования другими частями приложения или аналитикой (READ) - сервер запрашивает данные у датчиков
4) Авторизация и профиль пользователя

Пока что нет в системе:
5) Система алертов - например, если датчик влаги зафиксировал протечку или температура достигла целевой или дымоуловитель сработал и тд
6) Настройка сценариев работы - например, включить свет по расписанию

### **4. Проблемы монолитного решения**

- Масштабируемость - только через запуск дополнительных копий приложения, нельзя регулировать нагрузку на отдельные части приложения и выделять больше ресурсов куда-то, а куда-то меньше
- Сложно расширять функциональность - требуется высокое понимание системы и того как одни части влияют на другие части приложения 
- Нет четкого разделения по командам - тк работы одних команд сильно влияет на другие команды, сложно координировать процесс разработки, удлиняются сроки работы
- Низкая отказоустойчивость - если откажет часть монолита, то упадет все приложение целиком

Если вы считаете, что текущее решение не вызывает проблем, аргументируйте свою позицию.
Возможно текущее решение и подходило для того уровня развития, которое было до того как потребовалось серьезное улучшение системы вслед за ростом бизнеса, но сейчас оно уже не выглядит достаточным
